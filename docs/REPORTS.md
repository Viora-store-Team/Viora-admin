# البلاغات (Reports) وكيف يتعامل معها الأدمن

> مبنية على الكود الفعلي: الباك إند `src/modules/reports/` ولوحة الأدمن `src/app/(panel)/reports/`.
> عقد الـ API الكامل بـ `API.md` (قسم «البلاغات») بريبو الباك إند.

## 1) الفكرة بسطرين

الزبون بيبلّغ عن **متجر**، والأدمن بيشوف البلاغ ويقرر: **معالَج** أو **مرفوض**.
البلاغ **ما بيلمس المتجر**: الإيقاف أو الرفض قرار منفصل من شاشة المتاجر. البلاغ دليل بين إيدك، مش زر.

## 2) رحلة البلاغ

```text
الزبون (تطبيق الموبايل)          الباك إند                         الأدمن (لوحة الأدمن)
──────────────────────          ─────────                         ────────────────────
صفحة المتجر ← «إبلاغ»
اختيار السبب (+ وصف لو «سبب آخر»)
        │  POST /api/reports
        └──────────────────────► يتحقق من المدخلات
                                 يتأكد المتجر «قابل للبيع»
                                 يمنع بلاغ مكرر معلّق
                                 يحفظ البلاغ  status = PENDING
                                 يبعث إشعار جرس لكل أدمن فعّال ──► 🔔 «بلاغ جديد عن متجر 🚩»
                                                                  البلاغات ← فتح البلاغ ← مراجعة
                                 PATCH /api/admin/reports/:id ◄───  «تعليم كمعالج» أو «رفض البلاغ»
                                 status = RESOLVED | DISMISSED
```

## 3) من جهة الزبون

| البند | التفاصيل |
|---|---|
| المسار | `POST /api/reports` (جلسة زبون فقط) |
| الحقول | `targetType` = `STORE` · `targetId` = رقم المتجر · `reason` · `details` (اختياري) |
| الوصف `details` | حتى **300 حرف**. التطبيق بيظهر حقله فقط لما الزبون يختار **«سبب آخر»** |
| الحد | 20 بلاغ بالساعة من نفس الجهاز (`429`) |

أسباب البلاغ (`reason`) وكيف بتظهر للأدمن:

| القيمة بالـ API | النص بلوحة الأدمن |
|---|---|
| `FAKE_OR_SCAM` | متجر وهمي أو احتيالي |
| `COUNTERFEIT_OR_PROHIBITED` | منتجات مقلدة أو مخالفة |
| `INCORRECT_INFO` | معلومات المتجر غير صحيحة |
| `POOR_CUSTOMER_TREATMENT` | سوء التعامل مع العملاء |
| `INAPPROPRIATE_CONTENT` | محتوى أو صور غير مناسبة |
| `OTHER` | سبب آخر |

قواعد بتأثر على الأدمن:

- **بلاغ معلّق واحد لكل (زبون، متجر):** لو الزبون بلّغ وما انراجع بلاغه، محاولته الثانية بترجع `409 REPORT_ALREADY_PENDING`. بعد المراجعة بيقدر يبلّغ من جديد.
- **المتجر لازم يكون قابل للبيع** (موثّق وفعّال ومالكه فعّال)، وإلا `404`. يعني ما بتوصلك بلاغات على متاجر موقوفة أو مرفوضة من قبل الزبائن.
- النوع المدعوم حاليًا `STORE` فقط. حقل `targetType` موجود عشان يتوسّع لأهداف تانية بدون تغيير العقد.

## 4) من جهة الأدمن

### 4.1 كيف بتعرف إنه في بلاغ جديد

- **الجرس:** إشعار «بلاغ جديد عن متجر 🚩» فيه اسم المتجر والسبب (`ADMIN_STORE_REPORTED`، مع `reportId` و`storeId`). الإشعار بيوصل لكل الأدمنية الفعّالين.
- **الكارت:** «بلاغات مفتوحة» بالنظرة العامة = عدد البلاغات بحالة `PENDING`.

### 4.2 قائمة البلاغات (`/reports`)

| العمود | المعنى |
|---|---|
| النوع | نوع الهدف (متجر) |
| المحتوى | اسم المتجر المبلّغ عنه |
| سبب البلاغ | السبب بالعربي، وتحته **سطرين من وصف الزبون** لو كتب وصف |
| المبلّغ | اسم الزبون |
| الحالة | مفتوح · معالَج · مرفوض |
| تاريخ البلاغ | الأحدث أول |

- **فلتر الحالة:** الكل · مفتوح · معالَج · مرفوض. («مفتوح» بالواجهة = `PENDING` بالـ API.)
- **البحث `?q=`:** كل كلمة لازم تنطبق على **اسم المتجر** أو **اسم/إيميل/جوال المبلّغ** أو **وصف البلاغ**. من حرفين لحد 100 حرف، وحد أقصى 5 كلمات.
- الضغط على أي صف بيفتح تفاصيل البلاغ.

### 4.3 صفحة تفاصيل البلاغ (`/reports/:id`)

**كارد «بيانات البلاغ»:** السبب · المبلّغ · تاريخ الإنشاء · عدد البلاغات السابقة على نفس المتجر · ملاحظة المشرف · **وصف البلاغ** (نص الزبون كامل. لو ما كتب شي بيظهر «ما كتب المبلّغ وصفًا»).

**كارد «المحتوى المبلّغ عنه»:** اسم المتجر · المدينة · حالته · زر **«عرض المتجر»** بيفتح صفحة المتجر.

**«بلاغ سابق على نفس الهدف»** = عدد كل بلاغات هالمتجر ناقص هاد البلاغ. بيساعدك تفرّق بين شكوى وحيدة ونمط متكرر.

### 4.4 القرار

بس البلاغ `PENDING` بيظهر عليه زرين:

| الزر | الحالة الناتجة | متى تستخدمه |
|---|---|---|
| **تعليم كمعالج** | `RESOLVED` | البلاغ صحيح واتخذت إجراء (تواصلت مع المتجر، أوقفته، طلبت تعديل…) |
| **رفض البلاغ** | `DISMISSED` | راجعته وما لقيت أساس له |

- **ملاحظة المشرف (اختيارية):** كل زر بيفتح نافذة فيها حقل ملاحظة (حتى 1000 حرف). اكتب شو عملت أو ليش رفضت، أو اتركها فاضية. الملاحظة **داخلية** وبتظهر بكارد «بيانات البلاغ» بعد القرار، وما بتوصل للزبون ولا للتاجر.
- **المراجعة مرة وحدة بس.** لو أدمن تاني راجعه قبلك بنفس اللحظة، الرد `409 REPORT_ALREADY_REVIEWED` والصفحة بتعرض رسالة الخطأ. السبب إن المراجعة الثانية كانت رح تمسح ملاحظة وتوقيت الأولى.
- بعد القرار بينحفظ: من راجع (`reviewedBy`) ومتى (`reviewedAt`).
- **القرار ما بغيّر المتجر.** لو لازم توقف المتجر أو ترفضه، اعمل هاد من **شاشة المتاجر** (إيقاف/رفض).

### 4.5 دليل قرار سريع

| الحالة | الإجراء المقترح |
|---|---|
| بلاغ واحد، وصف غامض | افتح المتجر وشوف منتجاته وتقييماته. ما لقيت شي ← **رفض** |
| بلاغ واضح (احتيال، مقلّد) | **أوقف/ارفض المتجر** من شاشة المتاجر، بعدين علّم البلاغ **معالَج** |
| عدة بلاغات على نفس المتجر | ارفع الأولوية. اطّلع على «بلاغ سابق على نفس الهدف» وتعامل معها كلها |
| «سبب آخر» بلا وصف | ما في معلومات كافية. قرر حسب باقي المتجر |

## 5) الحالات

```text
PENDING ──► RESOLVED   (الأدمن اتخذ إجراء)
   └──────► DISMISSED  (الأدمن رفض البلاغ)
```

مفيش رجوع من `RESOLVED`/`DISMISSED` إلى `PENDING`.

## 6) مسارات الـ API

| المسار | من | ملاحظة |
|---|---|---|
| `POST /api/reports` | زبون | إنشاء بلاغ |
| `GET /api/admin/reports?status=&targetType=&q=&page=&limit=` | أدمن | القائمة، الأحدث أول، `limit` أقصى 50 |
| `GET /api/admin/reports/:id` | أدمن | التفاصيل + `targetReports { total, pending }` |
| `PATCH /api/admin/reports/:id` | أدمن | `{ "status": "RESOLVED" \| "DISMISSED", "adminNote"?: string }` (الملاحظة حتى 1000 حرف) |

أخطاء المراجعة: `400` حالة غلط · `404` مش موجود · `409` `REPORT_ALREADY_REVIEWED`.

## 7) حدود معروفة (مش أخطاء، بس اعرفها)

- **الأنواع `REVIEW` و`PRODUCT`** موجودة بواجهة الأدمن (وزر إخفاء التقييم)، لكن الباك إند حاليًا بيولّد بلاغات `STORE` فقط، فهاي الأزرار ما بتظهر عمليًا.
- **الوصف** مقصوص عند 300 حرف من الباك إند.
- **لا يوجد إشعار للزبون** بنتيجة مراجعة بلاغه. ولا الزبون ولا المتجر بيشوفوا `adminNote` أو مين راجع (داخلي).
- حذف المتجر من الأدمن بيمسح بلاغاته معه (`Cascade`)، لأن الحذف قرار الأدمن نفسه.
